# fnox evaluation

Date: 2026-11-08. Question: should countersign (a) fork fnox, (b) be built on
top of fnox, or (c) be built separately and borrow ideas? This answers
roadmap open question 4 ("Overlap with fnox"), which blocks the store.

**Recommendation: (c), build countersign separately.** Later, in Phase 3, add
a narrow optional backend that calls the `fnox` binary as a subprocess, so
`cnd` can serve values held in third-party vaults. No fnox crate is linked
into `cnd` or `cn`. The reasons are in section 4.

## 1. Architecture

### Process model

fnox is a CLI. It also has three optional long-running processes, all running
as the invoking user:

| Process | Started by | Lifetime | Role |
| --- | --- | --- | --- |
| Memory-cache daemon (`src/daemon.rs`, 3,163 lines) | `fnox` itself, automatically, when `[daemon] enabled` or `FNOX_DAEMON=on` | Until `idle_timeout` (default 8h) | Caches resolved values in RAM. One daemon per "socket key" (profile, `--no-defaults`, `--if-missing`, age key file; `crates/fnox-client/src/path.rs:44-110`). Socket in `$XDG_RUNTIME_DIR/fnox` or `/tmp/fnox-<uid>/`. |
| MCP server (`fnox mcp`, `src/mcp/`) | The agent's MCP client, over stdio | One MCP connection | Serves `get_secret`, `exec` and `request_secret` tools |
| Credential proxy (`fnox proxy run -- CMD`, `src/proxy/`) | The user | One child command | Local HTTPS MITM proxy that swaps placeholders for real values |

The daemon is a cache, not an authority. On a miss the CLI resolves the
secret **in the caller's own process** ("in your terminal") and pushes the
value to the daemon with `StoreResolved` (`crates/fnox-client/src/wire.rs:58-76`;
`docs/guide/daemon.md`, "Prompts and hardware keys"). Both ends refuse a peer
whose uid differs from their own (`crates/fnox-client/src/peer.rs:9-90`,
`check(peer_uid)` against `current_euid()`). The docs say so plainly: "Anything
running as your user can ask the daemon for cached values, just as it could
run `fnox get`" (`docs/guide/daemon.md`, Security).

### Configuration and where values live

- `fnox.toml` is discovered by walking up from the cwd. It merges with parent
  `fnox.toml` files, `fnox.<profile>.toml`, gitignored `fnox.local.toml` and
  the global `~/.config/fnox/config.toml` (`docs/guide/how-it-works.md`).
- Encryption providers (age, YubiKey, FIDO2, cloud KMS) keep **ciphertext in
  `fnox.toml`, normally committed to git**. Storage providers (1Password, AWS
  SM, Vault and others) keep only a reference. A `default` is plaintext.
- Private keys are user files, for example `~/.config/fnox/age.txt`. Lease
  ledgers live under `~/.local/state/fnox/leases/`, the audit log at
  `~/.local/state/fnox/audit.log`.
- Project config is partly attacker-controlled when a repo is cloned. fnox
  handles this case by case, for example by telling users to put `[audit]` in
  the global file (`docs/guide/audit.md`).

### Provider abstraction

- Trait `Provider` in `crates/fnox-core/src/providers/mod.rs:187-297`:
  `get_secret`, `get_secrets_batch`, `encrypt`, `put_secret`, `discover`,
  `capabilities`, `prepare`, `test_connection`, `auth_command`. It is async
  (`async_trait`).
- There are 29 provider definitions. Adding a built-in provider takes three
  steps: write a TOML descriptor in `crates/fnox-core/providers/<name>.toml`
  (fields, wizard text, category), write a Rust module in
  `crates/fnox-core/src/providers/`, and add it to the import list at
  `providers/mod.rs:160-166`. A build script
  (`crates/fnox-core/build/generate_providers.rs`) generates the closed
  `ProviderConfig` enum and the instantiate and wizard code. Providers are
  therefore compiled in; there is no runtime registry for Rust providers.
- Out-of-tree providers are Lua plugins: git repositories with a
  `provider.lua` (`crates/fnox-core/src/plugins.rs`, `providers/lua.rs`).
- Leases have a separate trait, `LeaseBackend`
  (`crates/fnox-core/src/lease_backends/mod.rs:34-62`: `create_lease`,
  `revoke_lease`, `max_lease_duration`, `cacheable`). There are 12 backends:
  AWS STS, GCP IAM, Azure, Vault, Cloudflare, GitHub App and OAuth, GitLab,
  Tailscale, Kubernetes, OAuth2 client credentials and a custom `command`.

### `exec` and injection (`src/commands/exec.rs`, `src/child_env.rs`)

`fnox exec -- CMD` merges config, resolves the secrets, applies
`json_path`/`line`, writes `as_file` secrets to 0600 temporary files, mints
leases and spawns the child with the inherited environment plus the secrets.
It removes `FNOX_AGE_KEY*` and the Enpass master password from the child's
environment, forwards SIGINT and SIGTERM, and exits with the child's status
(128+N on a signal; `exec.rs:340-355`). `--only` and `--except` narrow which
secrets are resolved (`src/secret_filter.rs`). Each secret's `env` field
decides where it goes: `true` means shell and exec, `"exec"` means exec only,
`false` means `fnox get` only (PR #604, from Discussion #578).

### Redaction (`src/redact.rs`, 237 lines)

- Aho-Corasick, leftmost-longest, with streaming carry-over across chunks.
  This is the same core idea as `countersign-hide`.
- Literal values only, trimmed. No base64, URL-encoding, JSON or hex variants.
  The docs say so (`docs/guide/running-commands.md:65`).
- The replacement is `[REDACTED]`, which does not say which secret matched.
  The minimum length is 3 bytes (`MIN_REDACT_LENGTH`); countersign uses 8.
- **Off by default** for `exec` (`--redact`, `redact_exec`,
  `FNOX_EXEC_REDACT`; `crates/fnox-core/src/config.rs:2095-2101`), and applied
  only to a stream that is not a terminal (`exec.rs:224-225`). It is on by
  default for MCP `exec`.
- There is no standalone pipe filter like `cn hide`. `fnox ci-redact` only
  prints `::add-mask::` lines inside CI (`src/commands/ci_redact.rs`).

### MCP server (`src/mcp/`, 2,405 lines)

- Three tools. `get_secret` returns the value. `exec` runs a command with
  secrets and returns its redacted output, capped at 1 MiB with a 300 s
  timeout. `request_secret` (off by default) sends the user a one-time link to
  a `127.0.0.1` page where they type a missing value; the value never passes
  through the agent (`src/mcp/request_secret.rs`, `src/mcp/page.rs`).
- `[mcp] tools` and `[mcp] secrets` are allowlists.
- Allowed secrets are resolved in one batch on the first call, so one YubiKey
  touch or SSO prompt covers the session. Values stay in memory until the
  stdio connection closes.
- **There is no list tool.** The server's `instructions` string
  (`src/mcp/server.rs:135-178`) does not name the available secrets. An agent
  using MCP alone cannot find out which secrets exist or what they are for.
- Under `fnox proxy run`, `fnox mcp` relays to the proxy process
  (`src/mcp/relay.rs`), and `get_secret` returns placeholders instead of
  values.

### Credential proxy and `--sandbox` (`src/proxy/`, 5,151 lines; `src/sandbox.rs`, 1,026 lines)

- Per-run HTTPS proxy on `127.0.0.1` with a session CA (`proxy/ca.rs`, rcgen)
  and a random proxy password in `HTTPS_PROXY`.
- Rules limit substitution by domain, method, path and one header or query
  parameter (`proxy/policy.rs`). Egress is strict by default.
- Destinations are checked against private, loopback and link-local ranges
  after DNS resolution, and fnox connects only to the addresses it checked,
  which defeats DNS rebinding (`proxy/destination.rs`).
- Echoed secrets are redacted from responses. Leases can be minted on demand
  and are revoked when the run ends (`proxy/leases.rs`).
- `PR_SET_DUMPABLE=0` is set on the proxy process (`src/proxy/plan.rs:18-19`).
- `--sandbox` on Linux uses `bwrap` with `--unshare-net/pid/ipc/uts` and
  `--die-with-parent` (`src/sandbox.rs:374-381`). A `fnox sandbox-bridge`
  forwarder exposes the proxy inside. fnox config, key files and common
  credential directories are hidden, `.git/hooks` and `.git/config` are
  read-only, and **`/run` is not mounted**, so a `cnd` socket under
  `/run/countersign` would be unreachable from inside without an extra bind.
- On macOS it uses `sandbox-exec`. It never falls back to running without a
  sandbox.

### Leases

See `LeaseBackend` above. Leases are cached per project in a user-owned
ledger and reused until 5 minutes before expiry
(`docs/guide/leases.md`, "How caching works"). The bootstrap credential can
sit behind a hardware key, so a touch is needed when a lease is minted.

### YubiKey and FIDO2

- These are **storage providers, not approvers**.
- `fido2` (`crates/fnox-core/src/providers/fido2.rs`, using `ctap-hid-fido2`)
  derives a key with CTAP2 hmac-secret and encrypts values into `fnox.toml`.
  It keeps the hmac-secret output in process memory, so a touch is needed
  once per process per provider.
- `yubikey` (`providers/yubikey.rs`, `yubikey_usb.rs`) does the same with
  HMAC-SHA1 challenge-response.
- Neither binds a touch to a described request. A touch unlocks a provider,
  not a named use.
- fnox-core's manifest says `ctap-hid-fido2 → hidapi → libudev` cannot be
  statically linked on musl, so musl builds leave FIDO2 out
  (`crates/fnox-core/Cargo.toml:79-82`). This is evidence for countersign's
  open question on the FIDO2 library: a statically linked `cn` cannot use
  that crate.
- Per-request approval exists only as a **preview**. PR #1132 (by jdalton,
  merged 2026-11-06) adds `native/touch-id-preview/` (about 4,150 lines of
  C++/Objective-C/TypeScript built by CMake, outside the Cargo build). It
  shows a dialog with command, project and secret names and checks Touch ID,
  Windows Hello, or fprintd over D-Bus on Linux
  (`portable/authorization_linux.cpp`). Its own text says it "never reads
  credentials or grants an authorization lease".
  `docs/proposals/macos-touch-id-approval.md` asks the maintainer whether to
  go further, starting with macOS Keychain items under an `LAContext`. The
  dialog runs in the user's own session as the user's uid.

### Audit log (`crates/fnox-core/src/audit.rs`, 267 lines; `docs/guide/audit.md`)

- Opt-in (`[audit] enabled` or `FNOX_AUDIT`). One JSON line per secret read:
  `ts`, `command`, `profile`, `config`, `secret`, `provider`, `cached`. No
  hash chain and no signature.
- Written to `~/.local/state/fnox/audit.log`, mode 0600, opened append-only.
  The path can be overridden from config or the environment.
- **The writer is the user's own process**, or the user's daemon, which since
  wire v7 writes entries for the reads it serves.
- Write failures are "logged and swallowed: auditing must never change
  whether a read succeeds" (`audit.rs:66-69`). countersign does the opposite:
  an action whose audit write fails is not performed (`docs/audit.md:110`).
- The docs state that it is not tamper-proof and suggest `chattr +a` or
  shipping lines to a remote collector.

## 2. Agent-friendliness against the beads `bd` bar

Scores run from 0 (absent) to 5 (as good as `bd`).

| Trait | Score | Evidence |
| --- | --- | --- |

The skill teaches configuring fnox, not which secrets this project has. |
| Discoverability: list with descriptions | 3 | Secrets have an optional one-line `description` (`config.rs:312`, settable with `fnox set --description`). `fnox list` shows it as a column, and `fnox env --json --describe` returns it per key with no values. **No usage-prose field. These are rendered as text on stderr. Only `env --json` emits a JSON error document (`ErrorDocument` with `kind`, `unknown`, `suggestions`). |
| Deterministic exit codes | 2 | Every error exits 1 (`src/main.rs` returns a `miette::Result`). `exec` and `proxy run` pass the child's status through, or 128+N on a signal. There is no table of exit codes by cause. |
| Short ids | 3 (mostly n/a) | Secrets are named by their env var. Lease ids accept a unique prefix (`src/commands/lease.rs:105,143`). |

Long `--help` with examples. `fnox usage` prints a KDL CLI spec and `fnox schema` a JSON Schema of the config. There is a skill, but no AGENTS.md snippet aimed at users. |

**Verdict: agent-aware, not agent-first.** fnox is very good at never
blocking on a prompt and at being honest in its docs. It is weak at the
structured contract `bd` has. The three biggest gaps:

1. **No uniform machine contract.** `list`, `get`, `check` and `doctor` have
   no `--json`. Errors are text, and every failure exits 1. An agent cannot
   tell "unknown secret" from "provider auth failed" from "sandbox missing"
   without parsing English, except through `env --json`.
2. **An agent cannot find out what a secret is for.** There is one optional
   description line and no usage prose. The MCP server, the channel built for
   agents, has no list tool, so a pure-MCP agent has to guess names or read
   `fnox.toml`.
3. **No priming.** Nothing prints, at session start, "these secrets exist,
   use them like this, never `get` them". The skill covers fnox in general,
   not the project's secrets.

**How an agent learns which secret to use today:** run `fnox list` and read
the table, or `fnox env --json --describe` (names, description, `env` mode,
injectable scopes, the file each comes from). After that it relies on
whatever the project's own docs say.

## 3. Fit with countersign's distinguishing properties

| countersign property | fnox today | Could it be added without rewriting the core? |
| --- | --- | --- |
| Daemon as a separate system uid owns the store | Daemon is a same-uid cache. Client and daemon refuse a different-uid peer (`fnox-client/src/peer.rs`). Every command loads config, key files and provider credentials directly in the caller's process. | **No.** Every read path assumes "fnox is you": config discovery from the caller's cwd, `~/.config/fnox`, age keys in the user's home, provider CLIs and SSO sessions of the user. A broker under another uid means the CLI must never touch any of these. That changes all 39 commands, the resolver and every interactive provider. |
| Grants bound to an agent session by process ancestry, with a TTL | Nothing. There is no `SO_PEERPIDFD`, pidfd, `/proc` walk or `getppid` anywhere in `src/` or `crates/`. "Session" means one MCP stdio connection or one `proxy run` child. | Only inside a broker that the agent cannot bypass. In same-uid fnox, the agent can run `fnox get` or `fnox exec -- printenv` (jdx says this in Discussion #578), so session binding would be advisory. |
| Per-grant approval through a channel the agent cannot drive | No approval per use. Touch and PIN unlock a provider. The native approval preview (PR #1132) is unwired and runs as the user, in the user's session. | The preview shows upstream wants approval prompts. But a prompt drawn by a same-uid process is drivable or forgeable by a same-uid agent: on X11 by synthesized input, and in every case by not calling fnox at all. countersign's answer (polkit with the logind session as subject, FIDO2 assertion over a request digest verified by a daemon the agent cannot reach) needs a separate-uid verifier, which fnox does not have. |
| Append-only, hash-chained audit log the agent cannot alter, fail-closed | Opt-in JSONL, user-owned, fail-open by design (`audit.rs:66-69`). No chain or checkpoints. | A hash chain could be added to `audit.rs` easily. Making it tamper-resistant needs a writer under another uid, which brings back row 1. Fail-closed contradicts the stated design rule. |
| `cn run` inject and scrub; `cn hide` on any pipe | `exec --redact` (literal only, off by default, `[REDACTED]`), MCP `exec`. No pipe filter. | Yes, these could be added, but `countersign-hide` is already implemented and stronger: encodings, per-secret named markers, an 8-byte minimum and newline flush. |
| Description and usage prose per secret | One-line `description`. | A `usage` field would be easy to add, and upstream would probably accept it **(unverified)**. |

### Would upstream accept them? (unverified judgement)

- The maintainer has the same goal but no mechanism. In Discussion #350
  (May 2026) jdx wrote: "I'd really like some sort of mechanism where the
  agent couldn't possibly access the secrets that doesn't involve a separate
  machine and http proxy but so far haven't come up with any great ideas for
  that."
- He also accepts requests quickly. "Paranoid mode" (#578) became `env =
  "exec"` in PR #604 within about ten days. The library API (#441) got
  "sounds fine". The agent skill (#873) shipped.
- But `docs/contributing.md` says "fnox has a deliberate scope and design
  direction. A change may be declined because it does not fit, introduces too
  much complexity". fnox installs through mise as one user binary, supports
  Windows and macOS, and needs no root.
- A root-installed system user, sysusers, socket and service units, a polkit
  action, udev rules and a root-owned approver registry are a different kind
  of product. Upstream would most likely accept the small pieces: `list
  --json`, an MCP list tool, a `usage` field, and an approval hook in the
  direction of PR #1132. The broker would most likely be declined or
  reshaped. That is a judgement, not something asked.

### License

fnox is MIT and countersign is Apache-2.0.

- **Fork or copy code:** allowed. MIT code can go into an Apache-2.0 project
  if the MIT copyright and permission notice is kept with the copied parts,
  for example in a `NOTICE` or `THIRD_PARTY` file and a header on copied
  files. The combined work can ship under Apache-2.0 for our parts.
- **Depend on fnox crates:** allowed with no obligations beyond keeping the
  notice in distributed binaries.
- **Contribute upstream:** patches would be under MIT, so Apache-2.0's patent
  grant does not carry over to them. That does not matter for small patches.

## 4. Recommendation

### The strongest argument for each option

- **(a) Fork.** Day one would bring 29 providers, 12 lease backends, a tested
  MITM proxy with DNS-rebinding defence, a bwrap/seatbelt sandbox, an MCP
  server with URL elicitation, and 801 unit tests, under a license that
  allows it. **Against:** the fork would split at the core, because the
  same-uid assumption is in every command. At about 140 upstream commits a
  month and a wire protocol that changes monthly, a fork stops being
  mergeable within weeks. We would maintain 75k lines, 812 crates and three
  platforms to get a Linux-first broker.
- **(b) Build on top.** countersign's Phase 3 includes proxying third-party
  vaults, which is fnox's core competence, and fnox exposes two integration
  surfaces: the `fnox-core` crate (`Fnox::discover/get/list`) and the
  versioned `fnox env --json` document. **Against linking `fnox-core` into
  `cnd`:** it has no Cargo features, so the hardened, AF_UNIX-only,
  no-capability daemon would carry cloud SDKs, a Lua runtime, vendored
  OpenSSL and SQLCipher, and dbus, from a crate whose API calls itself
  CLI-shaped and changes weekly. That is the opposite of a small trusted
  core. **Against shelling out as uid `countersign`:** it works only for
  providers that can authenticate without a user session (age, static tokens,
  Vault or AWS credentials). 1Password desktop integration, SSO browser
  logins and fnox's FIDO2/YubiKey providers do not fit a headless system user
  **(unverified; not tested)**.
- **(c) Build our own.** Everything that makes countersign worth building has
  no counterpart in fnox's code: the separate-uid daemon, process-ancestry
  sessions, approvals bound to a request digest, and a chained, fail-closed
  audit log. The parts that do overlap are either already built and stronger
  in countersign (`countersign-hide`) or small (a single encrypted store file
  of tens to hundreds of secrets). Building on fnox would mean working against
  its central assumption, not extending it.

### Decision

**(c), with one bounded integration later.**

1. **Phase 1 and 2: no fnox dependency.** Build the store, sessions,
   approvers, audit, `run` and `hide` as designed. This settles roadmap open
   question 4 for the store: countersign keeps its own.
2. **Phase 3, optional `fnox` backend in `cnd`.** If the vault-proxy
   direction goes ahead, add it by subprocess, not by linking.
   - A secret's record names `backend = "fnox"` and a key.
   - On an approved `run`, `cnd` (or a separate `countersign-fetch` helper
     unit with network access, so `cnd` keeps `RestrictAddressFamilies=AF_UNIX`)
     runs `fnox --non-interactive --no-daemon -c /var/lib/countersign/fnox/fnox.toml env --json --for exec --keys KEY`
     as uid `countersign`, with a fixed environment.
   - It parses the `schema: 1` document (`crates/fnox-client/src/document.rs`
     types can be used as serde shapes; `fnox-client` is a light dependency)
     and returns the value to `cn` under the normal grant.
   - Approval, session binding and audit stay in countersign. fnox becomes a
     fetcher for vaults countersign does not implement.
   - Pin the fnox version, because the CLI and document are moving fast.
3. **Upstream, optionally.** `fnox list --json`, an MCP `list_secrets` tool
   that returns names and descriptions, and a `usage` field would help any
   agent using fnox and cost us little. They are not on countersign's
   critical path.

### What to reuse from fnox, concretely

No crates. These ideas and reference code (MIT, so keep the notice if code
is copied):

| From fnox | Use in countersign |
| --- | --- |
| `env = true \| "exec" \| false` tri-state (PR #604) | Per-secret flag for "never injectable, reveal only" and "exec only"; maps onto `use` / `reveal` modes |
| `fnox env --json --describe` document: `schema` number, `#[non_exhaustive]`, `KeyRejection { unknown, suggestions, not_injectable }` (`crates/fnox-client/src/document.rs`) | Shape of `cn list --json` and of the `unknown_secret` error detail; add "did you mean" (`crates/fnox-core/src/suggest.rs`, strsim) |
| `request_secret`: one-time `127.0.0.1` page, single submission, 10-minute expiry, agent-written text labelled as such, MCP URL-mode elicitation (`src/mcp/request_secret.rs`, `src/mcp/page.rs`) | `cn add` started from inside an agent session (where `!` has no TTY); the page would be served by `cn` as the human, and the value still goes through `mutate` approval |
| `exec` pipe handling: helper threads per stream, stop waiting after 2 s idle when a background process keeps the pipe open, drain after a write error, SIGPIPE set to default in `main` (`src/commands/exec.rs:276-303,419-428`; `src/main.rs`) | `cn run` edge cases not yet in `docs/design.md` section 7 |
| Proxy: per-run CA, proxy password, rule matching, post-resolution IP checks, response redaction (`src/proxy/ca.rs`, `policy.rs`, `destination.rs`) | Tier 3 egress proxy, if built; a reference design with a client compatibility table already measured |
| bwrap argument set and hidden-path list (`src/sandbox.rs:374-381` and around) | Tier 2 launcher. Note: it drops `/run`, so a `cnd` socket must be bound in explicitly |
| `ctap-hid-fido2` cannot be linked statically on musl (`crates/fnox-core/Cargo.toml:79-82`); hmac-secret derivation in `providers/fido2.rs` and `hw_encrypt.rs` | Input to approvers open question 3 (FIDO2 library) and the `fido2` key slot |
| Honest "what this does not protect" sections (`docs/guide/mcp.md`, `proxy.md`, `audit.md`) | Already countersign's style; keep it |
| Agent skill shipped with the binary (`skills/fnox/SKILL.md`) | The Phase 1 Claude Code skill; add a `cn prime` that prints project-specific secrets and rules, which fnox lacks |
