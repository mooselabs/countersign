# Decisions

Decisions the owner has agreed, newest last. A decision changes only by adding
a new entry that says which one it replaces.

| # | Date | Decision | Why |
| --- | --- | --- | --- |
| 1 | 2026-11-08 | Build a local, agent-first secret manager to replace plaintext `./.secret-*` files in project roots. | The files are plaintext, often world-readable, owned by the agent's uid, and unaudited; one `cat` puts a key into a model transcript permanently. |
| 2 | 2026-11-08 | Agents **use** secrets (`cn run` injects them into a child process) rather than read them. Revealing a value is a separate, rarer grant mode. | A value that enters model context cannot be recalled by any TTL. |
| 3 | 2026-11-08 | Ship `cn hide` as a final pipe that scrubs secret values from any output. | Commands echo credentials (verbose clients, error messages, env dumps); scrubbing at the end of the pipe catches what injection cannot. |
| 4 | 2026-11-08 | Approval requires a channel the agent cannot drive. Approvers are pluggable adapters chosen in config. First adapters: YubiKey (FIDO2) and a polkit desktop prompt. | `!` commands in Claude Code run as the agent's uid with its environment and no TTY, so the agent can type them too. Physical presence or a trusted display is the boundary. |
| 5 | 2026-11-08 | A small daemon (`cnd`) running as its own system user, plus a CLI (`cn`). | Only a different uid keeps the store and the audit log out of the agent's reach. |
| 6 | 2026-11-08 | Each secret carries a one-line description and a usage prose block. Hard limits (allowed executables, hosts) are optional and later. | Prose guidance gets most of the value for a solo developer; enforcement can follow. |
| 7 | 2026-11-08 | Audit log is append-only, hash-chained, owned by the daemon user; the agent may read it but not alter it. | Consent is only meaningful if its use can be checked afterwards. |
| 8 | 2026-11-08 | Local and solo-developer friendly first. Proxying third-party vaults and a credential-injecting egress proxy are a possible commercial direction later, not v1. | Prove the local tool before building a service. |
| 9 | 2026-11-08 | Name **countersign**; CLI `cn`, daemon `cnd`. | A human countersigns each grant. `sk` collides with skim and `cs` with Coursier and csound; no common package ships `cn` or `cnd`. |
| 10 | 2026-11-08 | License Apache-2.0 with DCO sign-off, no CLA. | Enterprise-friendly (the eventual commercial audience often bans AGPL), carries a patent grant, and still allows a separate closed commercial layer. |
| 11 | 2026-11-08 | Rust; Linux first (systemd, polkit, SO_PEERCRED, /proc); macOS later. | The owner's machines are Linux; the session-binding mechanisms are platform-specific. |
| 12 | 2026-11-08 | Repository `github.com/mooselabs/countersign`. | Owner's choice. |
| 13 | 2026-11-08 | What the polkit dialog asks for is the user's choice at setup: touch only (the owner's preference), touch and password, or password only. It is an install-time setting, because polkit has one PAM stack for every prompt on the machine. Replaces P4. | Different users weigh speed against a second factor differently; the spike showed touch-only works ([spike](../spikes/polkit-dialog/README.md)). |
| 14 | 2026-11-09 | Phase 1 has one approver, polkit. `use`, `reveal`, `mutate` and `export` each go through the polkit adapter with their own action (`export` uses the `mutate` action). The `fido2` approver, client-driven approval and FIDO2 store unlock move to Phase 2. Phase 1 unlocks the store with a master key sealed by `systemd-creds`, plus a recovery phrase slot. Replaces P1 for Phase 1. | The spike showed polkit works with a password or a key touch and shows the request. FIDO2 is still blocked on its library choice (roadmap blocker 3), and on its own its display is the terminal. One approver ships sooner. |
| 15 | 2026-11-09 | The polkit subject is `unix-process` for the session anchor (the long-lived agent process, such as `claude`), with its `pid`, `start-time` (field 22 of `/proc/PID/stat`) and `uid`. Config `[approvers.polkit] subject = "process" \| "session"`, default `"process"`. Documented limit: a same-uid agent can register its own authentication agent for that process (`pkttyagent --process`) and draw the prompt; it still needs the human's factor, so it spoofs the display, it does not bypass approval. Settles roadmap blocker 1 and narrows P3. | A `unix-session` subject aborts polkitd 127/128 ([polkit-org/polkit#699](https://github.com/polkit-org/polkit/issues/699), [spike](../spikes/polkit-dialog/README.md)). The process subject works today; `"session"` is there for when #699 is fixed. |
| 16 | 2026-11-09 | Linux 6.5 or later is required. `cnd` uses `SO_PEERPIDFD` and refuses to start without it; there is no `pidfd_open` fallback. Settles roadmap blocker 2. | The fallback has a pid-reuse window (threat model T8). 6.5 was released in 2023; the owner's machines run newer kernels. |
| 17 | 2026-11-09 | An insecure test mode exists only behind the cargo feature `insecure-test` (on `countersign-daemon` and `countersign-approve`), and only in debug builds: a release build with the feature fails to compile. It adds an `insecure-auto` approver (approves after a configured delay, or denies), lets `cnd` run as the same uid as its clients, take the master key from a plain file and listen on a socket path given on the command line. Every end-to-end test uses it. | End-to-end tests need a daemon, a store and an approver without root, polkit or a human. A compile error keeps the mode out of anything that could be installed. |
| 18 | 2026-11-09 | The owner installs countersign by running `packaging/install.sh` with sudo. Agents never run sudo or pkexec, never change `/etc`, systemd units, PAM or polkit on the owner's machine, and never trigger a real polkit dialog. Tests use a private `dbus-daemon` with a fake polkit authority. | Installing changes machine-wide security configuration; that is the human's act. A real dialog raised by a test could be approved by habit. |
| 19 | 2026-11-09 | The approval factor is chosen at install: `install.sh --factor password\|touch\|touch+password`, default `password`; the owner uses `touch`. There is no click-only factor. A phone push approver is considered for Phase 2. Refines decision 13. | polkit has no confirm-only mode ([polkit#463](https://github.com/polkit-org/polkit/issues/463)), and a prompt that needs no credential could be answered by an agent that registered its own authentication agent (decision 15). A phone that shows the request and signs the answer would be a display outside the desktop. |
| 20 | 2026-11-09 | The owner installs through `packaging/trusted-build.sh`: as root, it clones a named commit from GitHub into a root-owned tree (`/usr/local/src/countersign/<commit>`), builds it there with the distribution's Rust toolchain (`/usr/bin/cargo`, an empty environment, `--locked --release`), and runs that tree's `install.sh`. `install.sh` refuses a tree or binaries another user can change unless `--allow-user-tree`. The touch factors change the `polkit-1` PAM stack for the developer only; other users, root included, keep the distribution's stack. Refines decision 18, and narrows decision 13, which said the stack applies to every prompt on the machine. | `install.sh` runs as root, so whoever can change the files it installs or runs can run code as root through it; in the developer's checkout that includes any agent, `~/.cargo` and any `rustc` wrapper. With `pam_u2f` in front of every user, root's prompts asked for a key root has none of, and `pkexec` and every administrator dialog failed. |
| 21 | 2026-11-10 | While the repository is private, `trusted-build.sh` takes the source from a git bundle the developer makes (`--bundle FILE`) instead of an anonymous clone from GitHub. Root copies the bundle, clones it with object checks, checks out the commit the owner confirmed on github.com, and verifies HEAD and `git fsck`. Refines 20. | Root has no GitHub credentials. A bundle is plain data with no repository config or hooks, and the commit hash alone decides what is built. |
